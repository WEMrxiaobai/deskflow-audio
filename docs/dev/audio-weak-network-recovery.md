# 音频弱网恢复：第一阶段

本阶段处理断开原因记录、同会话媒体恢复、固定媒体预缓冲、会话生命周期，以及不阻塞键鼠的音频停止和重试。保留现有键鼠、原身份 TLS 控制及 Opus/SRTP 链路，不加入动态码率、FEC、自适应缓冲或新媒体框架。

源码中的保护条件是需要恢复的证据，不能据此认定现场每次中断都是网络故障。原因码描述检测条件，现场归因仍需结合时间戳、线程轮询间隔、迟到及丢包计数。

## 键鼠优先与故障隔离

音频是可独立停止、独立恢复的附加能力。音频异常、设备切换、换密钥、会话重试只作用于音频控制和媒体，不能调用 core 的 start/stop/restart。键鼠仍使用原来的超时、输入处理和按键状态逻辑；本轮键鼠文件只增加断开原因日志。

- GUI 不再 join 音频线程。停止立即设置原子停止标志并撤销当前会话的消息处理，声卡释放、静音恢复和守护进程退出继续在后台执行。静音守护进程原有的安全恢复流程保持，不能为了缩短停止时间强杀它。
- 音频任务独立持有策略原子变量、选项和邮箱，不捕获控件指针，也不在后台调用 GUI 日志对象。控件销毁后，晚到回调只写仍存活的共享状态；进程退出时原守护进程继续按父进程死亡/管道断开处理恢复。
- 旧任务完成清理前不创建新任务；进程内租约也覆盖旧窗口销毁后新建窗口的场景。如果驱动清理卡住，保持音频不可用，不叠加线程、声卡或守护进程来强行恢复。
- 普通停止和失败统一至少冷却两秒；定时 reconcile、远端邀请和状态变化共用同一入口检查。正常密钥退休的发起端不另加故障等待，仍需遵守对端的清理与冷却屏障。
- 冷却或清理期间至多保留一份来自可信控制连接的邀请，取消、替换、对端断开及销毁均擦除密钥；启动前重新核验连接、收听意图和有效期，避免丢弃邀请后对端空等整个握手超时。
- 界面只在音频任务存在时每 50ms 消费一次邮箱：邀请、恢复消息、可见状态各一个槽，转换日志最多八条，本机播放接管和密钥退休为黏性标志。通知过多时合并状态、丢弃最旧日志，不无限排队 Qt 回调。
- 继续使用有界媒体/PCM 队列，发送端丢弃过期采集，接收端丢弃迟到媒体并有限补偿；UDP 每轮最多处理 32 包，解码赶帧最多八个周期。资源不足允许音频丢包、静默或等待恢复，不通过修改键鼠行为维持音频。

这些约束限制了音频自身的工作和清理成本，**不等于已经证明双机上的鼠标和键盘没有卡顿**，也不声称实现动态降码率或操作系统级输入优先级保证。

## 媒体恢复

1. 偶发缺包仍使用原有有界 PLC/静音补偿，过期包直接丢弃。
2. 保留媒体时间线偏差大于 40ms、接收 worker 落后超过八个分包周期、超过一秒没有前进媒体的保护，分别记录 `media-timeline`、`decoder-stall`、`media-timeout`。
3. 支持恢复的两端通过原 TLS `state.recovery` 声明能力。接收端暂停旧时间线并清空过期 PCM，通过绑定当前 peer/session 与独立 worker 邮箱 的 `recover` 请求取得发送端最近已加密的序号和时间戳。
4. `resume` 必须匹配当前递增请求编号和请求发出时的引擎恢复轮次。每次进入新的重锚状态都递增轮次；即使同一批积压 UDP 内先恢复再偏移、Session 未观察到中间完成状态，也会立即废弃旧请求、旧授权及旧宽限，发出新编号请求。引擎授权接口返回是否实际生效，未暂停或轮次不匹配时拒绝；首包前的进度回复不能被上层记成已经授权。接收端保留原 SRTP 上下文，只在后续包通过认证、防重放、前进序号及时间戳连续性检查后重建播放时间线，重新预缓冲。同一恢复轮次只授权最初的位置，后续进度回复不抬高门槛，允许先回复、后到达的合法媒体完成恢复。声卡、音量及用户静音状态保持。
5. 已有媒体的恢复三秒没有可信回复时报告 `media-recovery-timeout`，由原机制重建会话。首包查询单独覆盖发送端初始化预算，见下文。收到授权但仍没有新媒体时，三秒后再次查询发送位置：位置不变表示发送端没有新媒体，继续静默等待；位置前进时再给媒体一秒到达宽限。宽限内媒体到达则继续运行，超时仍无媒体才报告 `media-unreachable` 并重建。同一轮次的宽限不会被后续回复延长，后续查询无回复仍受三秒超时限制。
6. 旧版对端不声明恢复能力，继续使用重建流程，不向旧键鼠协议添加消息。

声卡在静音时可能不产生回环采集回调，因此“没有媒体”本身不等于链路断开。等待期间，原控制连接的心跳、证书、信任及键鼠在线门控继续生效。用户主动停止、键鼠断开或信任撤销仍立即结束音频；本轮没有放宽这些授权条件。

首包可达性从接收端设备及引擎就绪、准备发送 ACK 时开始监测：一秒仍无认证媒体即通过同一控制通道查询。发送端收到 ACK 后才开始初始化声卡，且初始化期间无法处理恢复邮箱，因此首个无回复期限至少覆盖这五秒设备启动预算及其后三秒控制等待（正常轮询下约在接收端就绪后的第八秒到期），同时保留查询发出后的三秒等待。设备打开与首包等待共用同一启动预算常量；不能把接收端自己的初始化耗时也扣进发送端的预算。这个启动余量不因重试而累计，收到回复后的查询继续使用三秒期限。

回复中的 `hasMedia=false` 明确表示本会话尚未产生加密媒体，界面显示等待对方播放，继续每三秒查询；不能用零序号猜测静默。发送端明确已有媒体而接收端仍没有首包时，同样使用一次性的一秒到达宽限。旧对端未声明恢复能力时无法区分初始静默与媒体不可达，本阶段保留其兼容行为，不凭空触发循环重连。

接收循环出现明显停顿时，先执行调度保护再处理内核积压的 UDP，避免 CPU 停顿被批量旧包先触发的媒体偏移掩盖。日志同时记录 `worker_gap_ms`；这仍不是网络单向延迟测量。

## 固定缓冲实验

主程序和 Session 默认使用 **20ms 媒体预缓冲**；底层引擎独立诊断仍保留 5ms 默认基线。它增加的是压缩媒体包在 jitter 队列中的等待：

- 五毫秒分包下，媒体队列为 `8 + ceil(20/5) = 12` 包，同时调整到达时间记录容量。
- 初始播放、可信恢复后的播放期限与网络时钟使用同一预缓冲参数。
- 解码仍按播放期限推进，所以不把额外 15ms 堆到 PCM 环形缓冲中；PCM 容量 30ms、裁剪线 25ms、归一化播放目标 12ms 保持原模型。
- 参数仅在建立会话时固定，运行中不动态调节。20ms 是实验起点，不是两台物理电脑的端到端延迟承诺。

## 生命周期

| 对象 | 有效性 | 到期或失效处理 |
| --- | --- | --- |
| 协商邀请 | 默认十分钟，仅限制新建连接、派生新会话和握手 HELLO/ACK | 不再因邀请到期结束已连接媒体 |
| 已建立会话的停止权限 | 握手后冻结原 control key、nonce、SSRC 及邀请标识，只接受匹配的 STOP | 邀请到期后 STOP 仍有效；不能接受新 HELLO，也不能停止另一 nonce 的会话 |
| 活动音频会话 | 原 TLS 身份、信任、键鼠门控、用户开关及停止消息 | 失效立即请求停止，后台清理 worker 并恢复本机声音 |
| 媒体密钥 | 使用独立单调时钟，默认每小时退休；同时保留原 SRTP 序号耗尽保护 | 正常结束并由接收端重新协商新密钥、nonce 和 SSRC；发起端不叠加故障等待，仍遵守对端清理屏障 |

本阶段的密钥退休仍会重新建立媒体设备，**不声称已实现无缝热轮换**。旧版已运行程序仍可能按其旧实现每十分钟重建，两端均更新后才能获得完整新行为。

## 日志

- 键鼠客户端和服务端使用 `keyboard-heartbeat-timeout` 并记录配置阈值，不再把未及时收到心跳直接描述为对端已宕机。
- 音频控制区分心跳超时、socket 错误、写入积压、身份撤销、键鼠门控及主动关闭。
- 音频恢复进入、收到发送进度、当前轮次授权实际生效、恢复完成及异常退出时发出独立 `Diagnostic` 事件，正式 GUI 经有界邮箱在界面线程写入 `audio-diagnostic` 日志；含实际认证/解码、拒绝、迟到、丢包、欠载、恢复计数、`recovery_epoch` 和自上次快照以来的 worker 最大轮询间隔。该事件不更新界面，也不按秒刷日志。计数表示实际检测结果，不是估算网络丢包率。
- 失败原因与用户提示分开传递。只记录原因和统计，不记录媒体密钥、nonce 或控制消息正文。

## 回归范围

`audio-engine` 增加真实 Opus/SRTP 配合虚拟时钟的固定预缓冲测试：0..15ms 抖动、真实乱序与批交付，三类恢复原因、恢复后的预缓冲、用户静音保留及防重放约束。另外跨过 16 位序号回绕，检查十二包队列的到达统计仍准确，避免序号直接取模覆盖尚未播放的包。授权轮次测试直接断言首包前授权失败、当前轮次成功、刚恢复再偏移时轮次递增、旧轮次拒绝及新轮次重新授权，整个过程不清理防重放窗口。

`audio-preview-session` 使用合成音频和回环 UDP：基线与新版 GUI 一样启用恢复能力，稳定传输后暂停接收 worker 120ms，验证同一次邀请内恢复、无回复时的有界超时；短时旧端路径验证独立媒体密钥使用期结束，并检查发送端尚未产生首包时明确回复。`audio-preview-invitation` 真实等待短期邀请到期，检查新连接拒绝、活动 STOP 有效及篡改/旧 nonce 拒绝。

`audio-preview-synthetic-capture` 使用启用可信恢复的真实 Session，在发送 worker 注入三次 25ms 短暂停顿。接收端持续轮询，五秒内双方仍须发送/解码至少 600 包，仅一次邀请且不能出现 `media-timeline`；接收端自己偶发失去调度时，仍允许原调度保护及可信恢复处理。该测试检查发送端合成音源的媒体时钟：worker 迟到后必须保留原计划采集时间，每轮最多补交八块，四块采集队列及编码 worker 按原 10ms 年龄限制丢弃积压；不能重设下次采集时间而遗漏媒体槽，导致几次短暂停顿累积成虚假偏移。只恢复旧合成计时逻辑的反向验证在 5.04s 失败，记录 `media-timeline timeline=1 scheduler=0 worker_gap_ms=0.5331`，随后解码数量不足；正式源码已恢复修复。真实声卡采集路径、40ms 保护、队列容量和 600 包断言均未修改。

异步编解码、静音门及格式测试使用接口原有的零采集时间戳（没有设备墙钟），避免唯一一包在编码 worker 首次获得调度前过期，令测试永远等不到编解码输出。媒体帧年龄限制仍生效。`wallExpiredCaptureIsDiscarded` 单独构造真实墙钟已过期 11ms、媒体年龄尚小于两块的 PCM，断言它不进入编码、过期计数准确递增，且后续真实 SRTP 包的序号/时间戳保留过期槽位。没有修改生产过期逻辑，也没有取消过期覆盖；挂起 sink 的测试在异常栈展开时同样释放屏障，防止清理等待造成挂死。

`audio-preview-recovery` 单独覆盖六个有序场景：UDP 先到、进度回复先到后延迟 100ms 交付同一位置的媒体、既有流持续不可达、初始无采集静默、初始静默后开始播放、首包持续不可达。媒体缺失通过保护真实 SRTP 包但不交付模拟，检查有界退出原因、诊断字段及一次邀请内恢复。两种到达顺序通过线程间屏障及独立进度诊断确认，不靠随机竞争碰运气。

`audio-preview-recovery-timing` 单独覆盖四个场景：首个进度回复先于任何 UDP、既有流刚重锚便再次偏移、发送端第 4.9 秒才回复，以及首包查询始终无回复。前两个场景通过 observer 屏障暂停接收 worker，在其恢复处理前将两个真实 SRTP 包同时排入 UDP 队列，固定“建立/恢复时间线后立即偏移”的顺序；随后先注入旧请求回复，断言不能授权，再注入新轮次匹配回复并验证实际 Opus 解码继续、仅一次邀请。慢启动通过手工发送端延迟服务邮箱模拟，不打开真实声卡；无回复场景断言不早于约第八秒退出，且仍保留明确超时原因。仅这些较长回归提高合成诊断模式的 `testDuration`，默认仍五秒，正式共享运行期限不变。

`deskflow-paired-audio-control-tests` 增加原身份双向 TLS 上的真实恢复消息往返，结合 Session worker、合成音频及回环 UDP 验证恢复；保留原身份 pin、明文拒绝、撤销、重连和键鼠门控测试。

`deskflow-audio-worker-tests` 使用真实 AudioSharingWidget/后台任务包装器与合成 runSession 替身：用原子屏障挂起清理超过两秒，验证停止及析构不等待、GUI 定时事件继续、清理不重叠、跨窗口租约、晚到回调和本机播放原子变量寿命、两秒重试门槛，以及一万次状态/一百次诊断的有界邮箱。另以临时证书和独立信任配置建立真实双向 TLS，验证清理期间邀请保留/取消/恢复、停止共享后 TLS 仍连接。运行时将 openssl 可执行文件路径作为首个参数。

`audio-worker-send-legacy`、`audio-worker-send-recovery`、`audio-worker-receive-legacy`、`audio-worker-receive-recovery` 直接链接真实 AudioSessionWorker 和 Session，不替换媒体函数，也不链接 Qt。每项以合成声音和回环 UDP 运行五秒媒体时间，断言双方连接成功、发送/解码至少 600 包。四项分别覆盖收发角色与是否协商恢复能力：接收端才能安装 onReady，onRecovery 必须与恢复邮箱同时存在。后台清理替身测试只验证生命周期，不能替代这些真实参数校验和媒体传输测试。

这四项正向兼容测试使用进度屏障控制媒体时钟：两端每轮报告实际计数，采集块已经发送/丢弃/过期且已发送 UDP 全部认证后，才允许推进 1ms。不能用推进时钟跳过尚未执行的编码或网络接收；实际 socket、Opus、SRTP 和参数校验仍运行。握手、编码队列的 10ms 过期保护及外层九秒看门狗继续使用真实时间，失败/析构会取消屏障并唤醒对端，避免留住后台任务。`testClock` 仅允许 `test=true` 且不访问设备，正式共享及真实声卡诊断传入该选项会被拒绝；输出明确标记 `stepped_media_clock=1`。

该设计使正向协议测试不依赖 Windows 恰好在 40ms 内调度 worker，**不证明旧端在真实调度停顿后能够会话内恢复**。40ms 时间线保护、八包周期调度保护仍由原虚拟时钟引擎测试精确验证；120ms 实际停顿、恢复超时、首包慢启动及媒体不可达等 Session 测试继续使用真实时间，没有启用这个时钟，也没有降低媒体数量或保护阈值。

这些测试不打开声卡、不改变真实网络、不修改已安装程序的信任记录。GUI 采用隔离 Qt 工程：编译真实音频控件和控制实现，core 仅提供未调用的信号符号替身，未启动实际 core；不能据此宣称真实键鼠输入已验收。跨机 Wi-Fi 听感、物理延迟、实际断网/网卡切换和长时间运行仍需实测。局部编译和隔离测试不等于完整安装包、部署或业务验收。
